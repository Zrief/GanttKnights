# GanttKnights 插件化路线

> 目标：把当前 CLI 工具（matplotlib 甘特图生成器）改造成 **AstrBot 插件**（指令 + 定时推送 +
> `_conf_schema.json` 配置），同时保留 CLI 用法；并**准备上架插件市场**（2026-09-14 起，见 §10 阶段七）。
>
> **不做**：`pages/` 图形设置页（`_conf_schema.json` 的表单够用）、为分发做字体子集化（不随包字体，用不着）。
>
> 本文是决策与执行依据。所有结论都标注了取证位置（本仓库 `文件:行`，或两个参考仓库的具体模块），便于后续核对。

## 1. 结论速览

| 决策点 | 选择 | 理由 |
|---|---|---|
| 插件形态 | **功能型 Star 插件**：聊天指令 + 定时推送 + 运维数据 | 产品是「一张图」，图的天然投递口是聊天群 |
| 出图方式 | **阶段一保留 matplotlib**，不改渲染内核 | 已有 601 行像素级排版是核心资产，重写等于推倒重来 |
| 渲染执行 | `asyncio.to_thread` + 单飞锁 + Agg 后端 | matplotlib 是同步 CPU 密集，直接跑会卡死事件循环 |
| 重复请求 | **不留缓存，按需重画**（阶段五晚定案，§17.4）；每天真正的产出是**与昨天的数据日差**（合并侧产出 → `src/数据变化.py` 落盘） | 机器长期开机、渲染 1.4s、请求低频——"少画一次"不值得 380 行缓存与它的 8 类 bug；"今天和昨天比变了什么"才是用户每天要的答案 |
| 字体 | **不随包字体**（2026-09-14 起）：三层候选 = 随包（可放可不放）→ AstrBot `data/font*.ttf` → 平台字体（雅黑/苹方/Noto CJK） | 缺字体不再出豆腐块；分发不受体积影响 |
| 配置界面 | **只用 `_conf_schema.json`**，不做 `pages/` | 本地自用，WebUI 自动生成的表单够用 |
| 分发 | **上架插件市场**（2026-09-14 改为待办，见 §10 阶段七） | 不随包字体后压缩包 3.55MB，16MB 上限不再构成约束；剩下的只是市场规范项 |
| AstrBot 版本下限 | `>=4.9.2`（若不用 `self.name` 则可更低）；实用下限 `>=4.17.0` | 见 §9 版本敏感点 |

**明确不做**（见 §11）：注入/改写 AstrBot Dashboard 的 `index.html`；写宿主 `localStorage` 的主题键；把大段 JS 塞进 Python f-string；锁死依赖版本。

## 2. 边界（本地自用 + 准备上架）

**做**：

1. AstrBot 插件形态：`Star` 子类 + `@filter.command` 指令 + APScheduler 定时推送。
2. 配置走 `_conf_schema.json`，由 AstrBot WebUI 自动生成表单。
3. 保留 CLI（`python cli.py`），与插件共用同一套渲染内核。
4. **准备上架插件市场**（2026-09-14 起）：补 `metadata.yaml` 的市场字段、按规范写 README、
   核对打包体积。详见 §10 阶段七。

**不做**（以及为什么现在可以不做）：

| 不做的事 | 原本的驱动力 | 现在 |
|---|---|---|
| `pages/settings/` 图形设置页 | 复杂的图库/预览交互 | 本地自用，`_conf_schema` 表单够用；市场也不强制 |
| 字体子集化 | 市场压缩包 16MB 上限 | **已经不需要**：2026-09-14 起不随包字体（分发内容 3.55MB），字体走三层候选 |
| 多平台适配声明**之外的**市场元数据定制 | 市场检索/分类 | 只补市场要求的 `support_platforms` / `tags`（§6.1），不做 i18n、不自建 logo |
| 为压缩体积裁剪背景图 | 打包上限 | 3.0MB 不是瓶颈 |

**仍然必须做的**（与上架无关，是插件能否加载的前提）：

- `requirements.txt` 里**只写裸依赖名**（matplotlib、numpy）。参考物 `astrbot_plugin_ark_calendar` 曾锁 `aiohttp>=3.14.3,<4` 与宿主 AstrBot 的 `aiohttp==3.13.5` 冲突，最后移除全部版本锁。**锁版本与是否上架无关，是本地也会炸的坑。**
- `matplotlib.use("Agg")` + `MPLCONFIGDIR` 指向可写目录（详见 §5.5）。
- 依赖 pip 安装：AstrBot WebUI 的「安装依赖」按钮会装 `requirements.txt`。

### 体积预算（2026-09-14 实测）

| 项 | 体积 | 说明 |
|---|---|---|
| **分发内容合计**（git 跟踪的 38 个文件） | **3.55MB** | 远低于市场 16MB 上限；其中 `背景图/` 3.0MB 是大头 |
| `src/` + `插件/` + 根脚本 | 129 + 20 + 331KB | 代码本体约 0.5MB |
| `docs/` + `README` | 73KB | 路线文档 + 配色规范 + 使用说明 |
| `字体/`（完整 CJK） | **0（已删除）** | 不随包；缺字体时走三层候选的平台字体，要跨平台一致再把 4 个文件放回 `字体/`（约 34MB，`.gitignore` 已排除） |
| `背景图/` | 3.0MB（2 张） | 进 git，换机器自动带到 |
| `数据/` | 运行时增长 | 用户数据，与代码分离 |
| matplotlib + numpy | 由 pip 装 | `requirements.txt` |

> 结论：**16MB 上限不再构成任何约束**（去字体后 3.55MB）。若将来要上架，剩下的不是体积问题，
> 而是市场规范项（`metadata.yaml` 的 `support_platforms` / `tags`、README 字段说明等，见 §14.1）。

## 3. 两个参考物的定性（以及为什么选 ark_calendar 那条路）

### 3.1 `astrbot_plugin_ark_calendar`（罗德岛行动终端）——功能型插件

`C:\Users\22378\AppData\Local\Temp\ark_calendar_ref`，v0.9.9。

- **骨架**：`main.py:175` `class ArkCalendarPlugin(Star)`，`main.py:182` `def __init__(self, context: Context, config: AstrBotConfig)` + `super().__init__(context)`；`initialize()`（`main.py:214`）/ `terminate()`（`main.py:252`）生命周期；13 个 `@filter.command`（`main.py:328` 起）；管理员命令叠 `@filter.permission_type(filter.PermissionType.ADMIN)`。
- **分层**：`main.py`（命令+调度）→ `core/`（业务/渲染/缓存/推送）→ `sources/`（纯 HTTP 取数），依赖全部构造函数注入；`sources/*` **从不 import astrbot**。
- **出图**：**不是 matplotlib**，是 Jinja2 HTML 模板 + AstrBot 官方 T2I `plugin.html_render(template, data, return_url=False, options=...)`（`core/renderer.py:289-327`）。Pillow 只用在输入侧缩放（`core/image_scale.py`）。
- **配置**：`_conf_schema.json`（43KB，10 个 `object` 分区）→ `AstrBotConfig`；`config_value(config, section, key, default, legacy_key)` 访问惯例（`core/config.py:30-42`）支持回落到顶层扁平旧键做迁移。
- **缓存**：业务语义签名（`core/render_cache.py:96-123`，**剔除 `generated_at`/`refresh_quality`**）+ `display_config` 纳入配置项（改配置自动失效）+ manifest 原子写 + 按签名引用计数的锁池（`core/image_cache_manager.py:139-154`）。
- **调度**：`AsyncIOScheduler(timezone=ZoneInfo("Asia/Shanghai"))`；**全部任务数为 0 就不 start 并把 `self.scheduler` 置回 None**（`main.py:855-865`）；稳定 job id + `coalesce=True` + `max_instances=1` + `misfire_grace_time`；每个任务一把 `asyncio.Lock`，任务体开头 `if lock.locked(): return`。
- **代价**：`main.py` 仍有 1381 行；AI 工具用了非文档化的 `astrbot.core.agent.tool` 内部路径（它自己写了 `_unregister_ai_tools()` 防御 reload 失效）。

### 3.2 `astrbot_plugin_palette`（AstrBot 调色盘）——美化型插件

`https://github.com/Sisyphbaous-DT-Project/astrbot_plugin_palette`，v0.4.17。

三条腿：官方骨架 + 官方 `pages/` 设置页 + **运行时物理改写 Dashboard `index.html`**。

- `__init__.py` 只有一行 docstring，入口是 `main.py`：`@register(PLUGIN_NAME, AUTHOR, DESCRIPTION, VERSION)` + `class PalettePlugin(Star)`，`__init__` 里直接 `ensure_dashboard_injection(self.paths)`（**实例化即打补丁**）。**全文没有 `initialize()`/`terminate()`/任何 `@filter`**。
- 注入机制：`INJECTION_START_MARKER = "<!-- astrbot_plugin_palette:start -->"` / `:end`（`palette/constants.py`），目标是 AstrBot 实际 serve 的 dist（优先 `--webui-dir` → 4.27+ 的 `resolve_dashboard_dist()` → 4.26 旧 helper → 回退 `data/dist`），做法是 tmp + `replace()` 原子写，并在 `</head>` 前插入标记块；写不进内置 dist 时整份复制到 `data/dist` + 写 `.palette-restart-required` 要求重启。
- 注入的脚本再从 `GET .../theme.css` 拉 **160KB 硬编码 CSS**（`palette/theme.py` 全是 `"\n".join([...])` 字符串字面量，无 base64/无生成资产，只有一个 `_stats_highlight_css` 函数横跨约 890 行），作用域靠 `html.astrbot-palette-active` 类 + `--astrbot-palette-*` CSS 变量。
- **还改写宿主的 `localStorage.themePrimary` / `themeSecondary`**，并为此维护一整套「保存旧值 / 还原」状态机 + 哨兵键。
- `palette/injector.py` 86.9KB = 约 620 行 Python + **约 1845 行内嵌在一个 f-string 里的 JS**（第 617 行到第 2461 行），所有 JS 花括号写成 `{{`/`}}`。
- **升级负债有硬证据**：`changelogs/v0.4.17.md` 整版只为「适配 AstrBot 4.28.0 透明化细节」+ 16 项回归用例；测试类名直接叫 `AstrBot428SurfaceTest`、`AstrBot428TransparencyDetailTest`。
- **结构性缺陷**：没有 `terminate()`，注入块只会被**替换**（幂等），**没有移除路径**，`index.html` 会一直带标记块直到 AstrBot 升级覆盖或用户手工从 `dashboard_backups/` 恢复。

### 3.3 为什么不走 palette 那条路

palette 唯一**值得我们借**的是它的 `pages/settings/`（官方 `pages/<name>/index.html` + `window.AstrBotPluginPage` 桥 + `context.register_web_api`）——**而这条腿完全不需要碰 Dashboard 文件**，天然稳定。它之所以要碰，是因为它的目标是**改造 AstrBot 自身外观**，那不是我们的需求。

我们不借的部分，理由都是硬的：

| 不借 | 理由 |
|---|---|
| 改写 Dashboard `index.html` | 无官方 API，属「就地打补丁」；每次 AstrBot UI 发版都要重对几百个 Vuetify/页面级选择器 |
| 写宿主 `localStorage` 主题键 | 碰别人的状态，需要一整套保存/还原状态机；与宿主未来主题 API 冲突会很难看 |
| 1845 行 JS 塞进 Python f-string | 放弃类型检查、lint、sourcemap、IDE 补全；只能靠 `node --check` + 函数体字符串位置断言兜底 |
| 16MB 级硬编码选择器表 | 维护成本按「每个 AstrBot 版本一次」计 |

唯一需要**警惕的相似性**：我们也会有一份「对外契约」（指令名、配置键、数据目录、图片格式）。这份契约要靠测试钉住，而不是靠人工核对——见 §8。

## 4. 目标架构

保留 CLI，新增插件适配层。**渲染内核（`src/`）不认识 AstrBot**，这样 CLI 与插件共用同一条流水线。

```
GanttKnights/                        # 插件目录（本地放在 data/plugins/ 下；目录名与 metadata 的 name 保持一致更省事）
├─ __init__.py                       # 新增，插件包标识（故意只放 docstring，不做任何导入）
├─ main.py                           # 改造：AstrBot 插件入口（Star 子类）
├─ cli.py                            # 由现 main.py 改名而来：保留 CLI 入口
├─ metadata.yaml                     # 新增：插件元数据
├─ _conf_schema.json                 # 新增：配置 schema
├─ requirements.txt                  # 新增：裸依赖名，不锁版本
├─ src/                              # 渲染内核（不认识 AstrBot）
│   ├─ __init__.py                   # 新增
│   ├─ config.py                     # 改造：Settings 支持注入路径
│   ├─ 流水线.py                      # 新增：把 cli.py 的 6 步流程收成 render_once()
│   ├─ 字体.py / 绘图_*.py / 解析_*.py / 汇总_活动.py / 筛选_活动.py / 生成_警告.py
│   └─ ...
├─ 插件/                              # 新增：AstrBot 适配层
│   ├─ __init__.py
│   ├─ 指令.py                       # CommandSpec（命令元数据单一来源）+ 帮助文本
│   ├─ 配置.py                       # _conf_schema → 运行配置（读取处夹取越界值）
│   ├─ 文案.py                       # 用户可见文案常量
│   ├─ 渲染.py                       # 渲染服务：Agg + to_thread + 单飞锁（**不留缓存**，§17.4）
│   └─ 推送.py                       # 每日推送：APScheduler + 会话记忆 + 幂等记账（阶段五）
├─ docs/插件化路线.md                 # 本文
└─ 数据/ 背景图/ 字体/                # 本地资产（不进 git；插件直接在原位使用）
```

> 阶段四曾有过 `插件/缓存.py`（签名 + manifest + 跨日失效），**已于阶段五晚删除**（§17.4）；
> 现在插件目录只有 `指令.py` / `配置.py` / `文案.py` / `渲染.py` / `推送.py` 五个模块。

**分层规则（单向依赖，照抄 ark_calendar）**

```
main.py (Star 子类)
  ├─ CommandSpec（命令元数据）
  ├─ APScheduler 任务注册与执行（阶段五）
  ├─ 配置读取包装（插件/配置.py）
  └─ 组装适配层对象
        ↓ 构造注入
插件/ (指令 · 配置 · 文案 · 渲染)
        ↓ 调用
src/ (渲染内核，纯 Python + matplotlib，无 AstrBot 依赖)
```

**关键不变式**：`src/**` 里 **不允许出现 `import astrbot`**。这样 CLI 永远可用，且内核可单测（参考物的 `sources/*` 就是这么做的）。

## 5. 必须处理的 7 个硬问题

### 5.1 `from src.xxx import` 会当场炸

以下模块全部使用绝对导入 `from src.… import …`，AstrBot 动态加载插件时 `src` 不在 `sys.path` 上：

`src/筛选_活动.py:8`、`src/解析_卡池.py:14`、`src/解析_API活动.py:12-13`、`src/绘图_图表.py:17`、`src/绘图_排版.py:39-43`、`src/绘图_主题.py:37`、`src/汇总_活动.py`（无 src 导入）、`src/字体.py`（无 src 导入）。

**处置**：全部改为相对导入（`from .config import settings` / `from ..config import settings`），并给 `src/` 与各子目录补 `__init__.py`。

> 注意包名含中文（`绘图_排版.py` 等）。Python 3 支持 Unicode 模块名，AstrBot 用 `importlib` 加载，**这部分可以不改名**；改名会牵动全仓库 import 与 git 历史，收益不足。

### 5.2 模块导入期有副作用（会在插件加载时直接失败或行为漂移）

| 位置 | 副作用 | 处置 |
|---|---|---|
| `src/绘图_排版.py:56-59` | import 时执行 `注册字体()` 并决定 `衬线` / `粗字重` 模块级常量 | 推迟到首次渲染（或 `initialize()`）；把 `衬线`/`粗字重` 改成函数返回（`衬线` 已于阶段三·补整条删除） |
| `src/config.py:34` | `settings = Settings()` 在 import 时把 `ROOT_DIR`（= 代码目录）钉死 | `Settings` 支持注入 `data_dir` / `asset_dir`；保留默认值以兼容 CLI |
| `main.py:27-28` | 模块级 `现在时间` / `现在字符串` 在 import 时求值 | 移入函数内（改名后的 `cli.py` 同处理） |
| `src/字体.py:26` | `字体目录 = Path(__file__).parent.parent / "字体"` | 改为可注入，默认值不变 |

### 5.3 路径必须搬家（代码目录 ≠ 数据目录）

**官方写法**（[插件存储](https://docs.astrbot.app/dev/star/guides/storage.html)）：

```python
from pathlib import Path
from astrbot.core.utils.astrbot_path import get_astrbot_data_path

plugin_data_path = Path(get_astrbot_data_path()) / "plugin_data" / self.name
```

- 优先用 `self.name`（AstrBot ≥4.9.2 可用）；拿不到时回落到硬编码插件名常量。
- **不要**照抄参考物的 `get_astrbot_plugin_data_path()`——那是内部 API，跨版本风险更高。

**目录划分**：

| 内容 | 位置 | 理由 |
|---|---|---|
| `所有活动数据.csv`、`新增预告.json`、`图片缓存/`、`警告.txt`、渲染产物 | `data/plugin_data/<plugin_name>/` | 用户数据，升级不覆盖 |
| 字体 | 插件目录（只读） | 本地资产（`.gitignore` 排除，需自行准备） |
| 背景图 | 插件目录（只读） | **已进 git**（`背景图/` 2 个文件跟踪），换机器自动带到 |

对应 `src/config.py:18-23` 的 6 个路径字段全部要支持注入覆盖。

### 5.4 字体（2026-09-14 起：不随包字体，走三层候选；不用衬线）

**现状：`字体/` 目录为空**（原来的 5 个文件已删除，约 60MB → 0）。渲染改用下面的三层候选，
本机（Windows）落到微软雅黑 + 雅黑粗体；要跨平台视觉一致，把这 **4 个文件**放回 `字体/` 即可：
`NotoSansCJKsc-Regular.otf` / `NotoSansCJKsc-Bold.otf` / `NotoSansMono-Regular.ttf` / `NotoSansMono-Bold.ttf`
（`src/字体.py` 的 docstring 有下载地址）。放回后出图与历史版本**逐像素一致**（实测 0 差异）。

**决定：不随包字体、不做子集化。** 三层候选已经能保证"任何平台都出得了中文"，于是
34MB 的随包字体从"必需"降级为"想要跨平台一致时才带的选项"；子集化更没必要（它会引入
"新增干员/活动名缺字"的长期维护负担）。

**决定：不使用衬线字体**（见 §10 阶段三·补的实测）。衬线只用在页眉大标题与底栏分区标签两处，
两处都是纯中文短串，而所有候选字体的汉字 advance 都是 1.000em → 换族对版面宽度零影响，纯审美选择；
反过来，旧代码在缺 `字体/` 时会退到系统 `Noto Serif SC`（可变字体 → ExtraLight(200)），标题反而更细。

只需要修**加载时机**（与 §5.2 同源）：

- `注册字体()` 从 import 期**推迟到首次渲染**，并且放在 `asyncio.to_thread` 里执行（它要扫字重、
  重建 matplotlib 字体缓存，是秒级阻塞）。
- `src/字体.py` 的字体目录取自 `settings`（阶段一已做成可注入），默认仍是插件目录下的 `字体/`。
- ~~`src/绘图_排版.py:57` 的 `衬线 = ...` 保持不动~~ → **该判断已整条删除**（不再有衬线族），
  顺带修掉了它"import 期求值、而字体注册已推迟到出图时"的时序不一致。
- 兜底链**已升级为"字体三层候选"**（随包 → 自定义槽 → 平台，2026-09-14）：
  见本节后面的"已落地：字体三层候选"。要点是缺 `字体/` 时不再出豆腐块。

> 字体子集化的完整方案（含实测体积、`--retain-gids` 的坑、OFL 改名要求、三平台系统字体宽度实测）已归档到 §14，供将来若改主意时参考。

**要不要改成"直接用 AstrBot 的 local 字体"？（2026-09-14 实测结论：不要，但理由不是审美）**

先纠正一个容易误导的度量：**像素差百分比不能当"视觉差异"用**。把字体从随包 Noto Sans CJK 换成
系统微软雅黑（AstrBot 的 local 策略在 Windows 会选的 msyh/msyhbd），像素差 **9.985%**——听起来很大，
但**版面一个像素都没动**：把两种字体下每一次文字绘制（内容 / 像素坐标 / 字号 / 对齐）逐条比对，
**86 条完全相同、0 条不同**；9.985% 全部来自字形轮廓与抗锯齿边缘（换任何字体都会有这个量级的差异）。

| 对照（固定背景/时刻） | 结果 |
|---|---|
| 文字绘制（内容/坐标/字号/对齐） | **86 / 86 完全相同** → 版面不受字体来源影响 |
| 像素差 | 9.985%（对照：去掉衬线是 1.277%）——纯字形与边缘差异，**不代表视觉差异大** |
| 日期刻度 `09/13` 一类的宽度 | Noto Mono 68.8px → 雅黑 63.5px（−7.6%）；但**雅黑的拉丁数字也是等宽数字**（`09/10`…`12/28` 全是 63.5px，极差 0.00px），日期轴带不会乱——先前"雅黑没有等宽、日期会不齐"的说法**是错的** |
| 活动名 `【标准池】#193 · 乌尔比安 / 仇白` | 489.2px → 487.3px（−0.4%） |

**真正的硬问题不是审美，而是"没有 `字体/` 时出的是豆腐块"。** 实测（`GK_FONT_DIR` 指向空目录）：
渲染不崩、也不报错，但整张图的中文全是 `囗`——因为我们的系统兜底链（`src/绘图_图表.py`）
只找 Linux 系家族（`Noto Sans CJK SC/JP` → `Droid Sans Fallback` → `AR PL UMing CN`），
Windows 上一个都没有，最终落到 matplotlib 默认的 DejaVu Sans（不含 CJK）。截图：`tmp/度量/空字体_估算.jpg`。

所以结论分两层：

- **不要 import AstrBot 的内部字体解析**：`astrbot.core.utils.t2i.local_strategy.FontManager` 是内部路径
  （4.28 刚被整体重写），返回 Pillow 字体对象（路径要从非契约的 `.path` 抠），`import` 实测 **575ms**。
- **抄它的候选表，而不是调它的类**（2026-09-14 已落地，见下）。

#### 已落地：字体三层候选（`src/字体.py`）

`注册字体()` 现在是"注册所有可用字体源 → 按角色解析 → 应用 rcParams"的单一入口
（结果按**字体来源指纹**缓存，不是一次性布尔），`绘图_图表.设置字体()` 已删除
（它过去每次渲染重复 `addfont` 同一支字体，matplotlib 3.11 不按路径去重
→ ttflist 每次 +1 条并清 findfont 缓存，实测 ~96ms/次）。

> **为什么必须是"指纹"而不是"只跑一次"（2026-09-14 审查实测）**：AstrBot 是长驻进程，
> "禁用插件 → 启用插件"**不会重载**已 import 的 `src.字体`。原本的一次性守卫让
> "先出图、后往 `data/font.ttf` / `字体/` 放字体"**在本次进程内永远不生效**，
> 而这是插件唯一暴露的自定义字体入口——用户只能靠"重启 AstrBot"。
> 现在 `字体指纹()` = 字体目录的文件列表(名,大小,mtime) + `额外字体` 各文件(路径,大小,mtime)
> + `font_path`/`font_family`；指纹变了就重解析（每次出图多付一次 stat，实测量级 0.1ms）。
> 审查者自己的探针复跑结果由 `False` 变 `True`：`同进程内新增的自定义字体被采用 = True`。
>
> 仍有的边界（要重启才收敛）：matplotlib 的字体表**只增不减**，
> 所以**删掉**字体文件后本进程内仍可能解析到旧路径；同名同字重的**不同文件**相争时
> `findfont` 平分取先注册的那个，也可能落到旧的。

| 层 | 来源 | 说明 |
|---|---|---|
| ① 随包 | `字体/` 下的 4 个静态字重（`字体表`） | 设计基线；命中即"逐像素与历史一致" |
| ② 自定义 | `settings.额外字体`（插件按 AstrBot 约定填 `data/font.ttf` / `font-bold.ttf` / `font-mono.ttf`）；或 `settings.font_path` + `font_family`（CLI 用 `GK_EXTRA_FONT_DIR`） | 官方文档化的插槽；**带字形闸门**：先查 `get_char_index('中')`，查不到就忽略并告警（否则整张图变豆腐块） |
| ③ 平台 | `无衬线候选` / `等宽候选`（抄自 `local_strategy.py:34-111`）：Noto CJK → `Microsoft YaHei` → `PingFang SC` → `Hiragino Sans GB` → `Noto Sans SC` → `Droid Sans Fallback` → `AR PL UMing CN` | 缺 ①② 时的兜底；等宽角色在 Windows/macOS 会落到雅黑/苹方（它们的拉丁数字是等宽数字，日期照样齐） |

`真粗体` 的判定同时改了：不再"看 `字体/` 里有没有 `NotoSansCJKsc-Bold.otf`"，而是
**"解析出来的 bold 文件 ≠ regular 文件"**——于是雅黑粗体、Noto CJK Bold 都算真粗体，
而"可变字体同一文件"（系统的 `Noto Sans SC`）会被正确地判为没有真粗体，调用方转同色描边兜底。

判据复核（固定背景/时刻）：

| 场景 | 结果 |
|---|---|
| 有 `字体/`（正常） | 解析到 `NotoSansCJKsc-Regular.otf` + `NotoSansMono-Regular.ttf`，真粗体 = `NotoSansCJKsc-Bold.otf`；出图与改造前 **逐像素 0 差异** |
| 无 `字体/`（`GK_FONT_DIR` 指向空目录） | 解析到 `msyh.ttc` + `msyhbd.ttc`（来源=系统），**正常出图、无豆腐块**；与"手工把字体全换成雅黑"的参照图 **逐像素 0 差异** |
| 插件侧无字体（模拟忘带字体） | 走同一路径：`/甘特图` 仍出 308KB 合法 JPEG，检查脚本全绿 |
| 约定槽放了不含中文的字体 | 告警并忽略，回落到平台字体（不会静默出豆腐块） |
| 约定槽放了中文字体 | 正文采用它（来源=自定义），等宽仍走平台候选，真粗体按文件比较判定 |

于是"是否随包那 34MB 字体"退化成一条纯取舍：**留着 = 跨平台视觉一致；不带 = 各平台用各自系统字体
（版面完全相同，实测 86/86 文字绘制一致）**。当前选择：**不带**（`字体/` 已清空，本机走雅黑）。

### 5.5 matplotlib 依赖与无头环境

- 官方 AstrBot `requirements.txt` 含 `pandas` / `pillow` / `httpx` / `apscheduler`，**不含 matplotlib / numpy** → 我们的 `requirements.txt` 至少要有 `matplotlib`、`numpy`。
- **必须 `matplotlib.use("Agg")`**（在 import pyplot 之前），插件环境无显示器。
- **必须提前设 `MPLCONFIGDIR`** 指向 `data/plugin_data/<plugin_name>/mplconfig/`（或临时目录）并确保可写：matplotlib 首次运行会写字体缓存，容器/只读环境里默认路径不可写会报错或反复重建缓存。
- 字体注册（`fm.fontManager.addfont`）会让 matplotlib 重建字体缓存，是**秒级阻塞**操作 → 只在首次渲染做，且在 `to_thread` 里做。
- 只写裸依赖名：`matplotlib`、`numpy`（`pandas`/`Pillow`/`httpx` 宿主已有，但写上更保底）。

#### ⚠️ 实测：加载期 1.3s 里，pandas 占 1.2s（比 matplotlib 更值得处理）

在 AstrBot 实例环境（Python 3.12.13 / AstrBot 4.28.0）逐个模块实测导入耗时：

| 导入项 | 耗时 |
|---|---|
| **pandas** | **1186 ms** ← 最大单笔 |
| numpy | 0 ms（已被 pandas 带入） |
| httpx | 83 ms |
| PIL | 1 ms |
| `src.config` / `src.汇总_活动` / `src.解析_*` | 1–2 ms |

**`src.流水线` 整体导入实测 1319 ms → 把 pandas 换成桩后降到 201 ms**（省 ≈1.1s）。

原因：`src/筛选_活动.py` 与 `src/生成_警告.py` 顶层 `import pandas`，而它们被流水线顶层导入。
pandas 在本项目里只用于纯 CRUD（读 CSV / `to_datetime` / mask 过滤 / `sort_values` / `iterrows`），

**结论：pandas 替换从"可选优化"升级为加载性能的关键项，排在阶段三之前做。**

在**未装 matplotlib** 的环境里实测：`src.config` 可导入，而 `src.字体` / `src.绘图_排版` /

### 5.6 阻塞调用会卡死整个 AstrBot

- `src/获取_prts.py:15` 是模块级**同步** `httpx.Client`，全流程同步（`请求()`、`获取事件列表()`、`下载图片()`）。
- matplotlib 渲染 2400px/dpi150 是秒级 CPU 阻塞。

在 `@filter.command` 的 async handler 里直接调 = 整个机器人卡住。

**处置**：

1. 整个「取数 + 渲染」流程包成一个同步函数，`await asyncio.to_thread(...)` 执行；
2. **单飞锁**：渲染期间第二次请求不应重复渲染。参考物用「按签名引用计数的锁池 + 锁内 double-check」（`core/image_cache_manager.py:78-96/139-154`），我们第一版用 `asyncio.Lock` + 锁内再查一次缓存即可；
3. 必须串行化：`src/绘图_排版.py:243` 与 `src/字体.py:66-68` 都在改 `plt.rcParams` 全局状态，pyplot 还持有隐式 figure 栈——**并发渲染会互相污染**；
4. 网络侧可保留同步 `httpx`（放在 `to_thread` 里就无害），不必改 async —— 但要在文档里写明这个取舍。

### 5.7 渲染耗时要用「先说话、后出图」兜住

- **每次都先发一句进度文案**，再出图（`event.plain_result` → `event.image_result`；handler 是
  **async generator，可以 yield 多次**，参考物 `main.py:338-339` 就是这么做的）。
  措辞覆盖两种情况："缓存命中（几十毫秒）"与"首次爬数据（十几秒）"。
- ~~命中当日缓存 → 秒回、不发文案~~：阶段四曾为此做了 `查现成图()` 预判（在事件循环里先算一次签名、
  查一次 manifest），阶段五按第一性原理**删掉了**——它为了少说一句话，复制了一条会与真判定分叉的
  判定路径（审查实测过分叉：8 张背景 40 次请求里 4 次"说不等却静默渲染 1.3s"）。
  代价只是命中时多一句文案（§17）。
- 参照 `src/流水线.py::今天写过()` 的新鲜度检查逻辑（文件存在且 mtime 是今天）——它决定"要不要联网抓"，
  但**不能**当缓存键，见 §7。

## 6. 插件骨架要做成什么样

### 6.0 入口文件与目录名的发现规则（已查源码确认）

来源：`astrbot/core/star/star_manager.py` 的 `PluginManager._get_modules()`：

```python
dirs = os.listdir(path)
# 遍历文件夹，找到 main.py 或者和文件夹同名的文件
for d in dirs:
    if os.path.isdir(os.path.join(path, d)):
        if os.path.exists(os.path.join(path, d, "main.py")):
            module_str = "main"
        elif os.path.exists(os.path.join(path, d, d + ".py")):
            module_str = d
        else:
            logger.info(f"Plugin {d} has neither main.py nor {d}.py; skipping it.")
            continue
```

**结论：入口有两个合法位置，且 `main.py` 优先。**

| 写法 | 例子（目录 `astrbot_plugin_ganttknights/`） |
|---|---|
| `main.py` | `astrbot_plugin_ganttknights/main.py` |
| 与目录同名的 `.py` | `astrbot_plugin_ganttknights/astrbot_plugin_ganttknights.py` |

**三个必须知道的推论**：

1. **目录名 = `metadata.yaml` 的 `name`**。`_get_plugin_dir_name_from_metadata()` 会用 metadata 的 `name` 去定位安装目录，且 `_validate_importable_name()` 要求它是合法 Python 标识符。
2. **两者同时存在时永远用 `main.py`**，同名的那个被静默忽略（`if/elif`）。这是个静默失败点。
3. 走 `main.py` 分支时**目录名不必等于文件名**，但**必须等于 metadata 的 `name`**；本仓库目录名 `astrbot_plugin_ganttknights` 与 metadata 的 `name` 一致，两条路都走不通时才需要改名。

**本项目的选择**（用户已确认，阶段三落地）：**插件入口用 `main.py`，CLI 挪到 `cli.py`**——就是 §4 的原始布局。

```
GanttKnights/                          # 目录名 = metadata.yaml 的 name
├─ main.py                             # 插件入口（Star 子类）
├─ cli.py                              # CLI（python cli.py 调试用）
├─ metadata.yaml                       # name: astrbot_plugin_ganttknights
├─ _conf_schema.json / requirements.txt
├─ src/                                # CLI 与插件共用
└─ docs/插件化路线.md
```

> 曾考虑过"保留 `main.py` 做 CLI、另建 `astrbot_plugin_ganttknights.py` 做插件入口"（`7e341f4` 记录的那条），**已否决**：
> 它把"哪个文件是入口"变成需要记住的隐规则，而收益只是 CLI 少改一次名字。代价对比：
> 改名的成本是 `cli.py` 里三行用法注释 + README 三行命令；收益是入口=约定、不留静默失败点（推论 2）。
>
> **导入方式的差别（重要）**：`cli.py` 以脚本方式运行（`__main__` 无父包），必须用**绝对导入**
> `from src...`；`main.py` 被 AstrBot 以 `data.plugins.<目录名>.main` 导入，必须用**相对导入**
> `from .src... / from .插件...`（§5.1）。两者不可互换。

> 目标机器上须把仓库放进 `data/plugins/astrbot_plugin_ganttknights/`（目录名与 metadata 的 name 一致）。

## 7. 缓存设计（⚠️ 已废弃，2026-09-14 晚）

> **本节连同它落地的 `插件/缓存.py`（~380 行）已经整个删掉。** 与用户对齐行为模型后的结论是：
> 这个插件每天真正要回答的是**"今天和昨天比变了什么"**，而不是"怎么少画一次"——
> 机器长期开机、渲染 1.4s、请求低频，"重复渲染"根本不是一个值得用 380 行和 8 类 bug 去换的问题。
> 现在改为**不留缓存 + 合并时直接产出日差**（`src/汇总_活动.py::合并差异` → `src/数据变化.py`），完整复盘见 **§17.4**。
>
> 下面保留的是当时的完整设计记录（含它与参考物的差异、实测数据），**作为历史与"我们试过什么"的留档**；
> 其中仍然成立的部分已在别处被继承：产物原子写（现在用在 `Gantt.jpg` 上）、发图前的魔数校验、
> 背景按自然日抽签（现在是为了观感稳定）。**不要照着本节重新引入缓存。**

**核心原则：签名 = 业务语义 + 影响画面的配置，剔除「元信息」。**

参考物 `core/render_cache.py:96-123` 的做法：
- 签名 = `sha256(json.dumps({"snapshot": <业务快照>, "display": <display_config>}, sort_keys=True))`；
- 业务快照**主动剔除 `generated_at`、`refresh_quality`**，来源状态规范化为固定字段 → **「数据没变但重爬了一次」不会击穿缓存**；
- `display_config` 纳入所有影响画面的配置项（时间窗、清晰度、输出格式…）→ **用户一改配置，旧图自动失效**，不用手写失效逻辑。

**我们必须额外注意的一条**：`src/绘图_主题.py` 的配色是**由随机选中的背景图推导**的（`main.py:205-207` 每次 `随机背景()` 取一张）。所以：

- 「随机背景」会让每张图都不同 → 缓存必失效；
- 处置：把**背景图的实际路径（或文件内容哈希）纳入签名**。这样「同一背景 + 同一数据」才能命中缓存。若要保留「每次换背景」的观感，应把它做成**显式配置**（`随机 / 固定 / 指定文件`），而不是隐式行为。

**配套三件套**（都值得抄）：
1. **成品校验后才入缓存**：只读文件头 8 字节判 PNG/JPEG 魔数（`core/render_cache.py:17-66`）；
2. **tmp + `replace()` 原子写**（`core/render_cache.py:159-209`）；
3. **跨自然日强制失效**：manifest 里 `expires_at = min(渲染时间 + max_age, 次日 00:00)`（`core/render_cache.py:186-197`）——比「缓存 N 小时」更符合日程图语义。

> **阶段三的临时物：复用窗口**（**阶段四已按本节方案取代**，见 §7.2 落地记录）。
> `插件/渲染.py` 当时先实现了最小可用版：`asyncio.Lock` 单飞 + 「最近一次渲染结果 + `reuse_seconds`
> 窗口（默认 60s，可配 0–3600）」。它只回答"刚刚才渲染过吗"，**不含签名、不校验成品魔数、
> 不跨日失效**；跨日由 `需要每日更新()`（数据新鲜度）兜住一半。配置键 `render.reuse_seconds`
> 与 `render.random_background`（关闭后固定用目录里第一张背景）都是阶段四签名缓存的预埋项——
> 前者已在阶段四删除，后者保留并成为"随机背景 × 缓存"这条设计的开关。

### 7.1 ⚠️ 陷阱：「现在时间」会驱动数据清理（本项目已真实踩中）

`src/汇总_活动.py` 的 `合并保存CSV` 用**调用方传入的时间**推导清理线：

```python
清理线 = (datetime.strptime(现在时间, "%Y-%m-%d %H:%M:%S") - timedelta(days=过期保留天数)).strftime(...)
所有 = [r for r in 已有.values() if r["结束时间"] >= 清理线]
```

即 **`现在时间` 不只是渲染参数，它还决定"哪些数据算过期"**。传入的时间偏新
（调试时注入基准/未来时间）会让所有条目被判过期，写回时就可能只剩表头，
**且原本没有任何报错**。

**发生过的真实事故**：阶段二验证时注入 `现在时间=2026-09-13`，21 条活动数据被清空为 0 条
（1620 字节 → 51 字节）。数据后来用 `python cli.py --bootstrap --force` 从 PRTS 完整抓回
（字节数与行数与原文件一致）。

**两条纪律**：

1. 调试时**绝不要**给会写数据的路径（`合并保存CSV` / `更新数据` / `render_once(强制刷新=True)`）
   注入未来或基准时间——`render_once(强制刷新=False)` 不写数据，注入时间是安全的。
2. 已加护栏 `src/数据保护.py`：写回前检查「已有条数 → 待写条数」，命中即**拒绝写盘并保留原文件**：
   - 已有非空而待写为空 → 拦截（一次清空，几乎必然是时间传错）；
   - 清理比例 > 50% 且已有 ≥ 10 条 → 拦截。

   确实需要大清理时显式传 `允许大幅清理=True`；`更新数据` 会捕获 `数据保护拦截` 并只告警，不中断渲染。

   > ⚠️ **护栏只保护活动数据 CSV。** `新增预告.json` 与 `警告.txt` 是覆盖写、**没有护栏**；
   > 图标缓存目录的孤儿清理（`_清理图标缓存`）也没有护栏。给这些路径注入时间是安全的
   > （它们不按时间裁剪内容），但不要用注入时间去驱动爬取。

### 7.2 落地记录（阶段四，2026-09-14）

本节方案已全部实现，代码在 `插件/缓存.py`（判定与落盘）与 `插件/渲染.py`（顺序与交付）。
下面第二张表是**当日对抗性审查 + 设计讨论之后的修订**（原方案 → 修订后），每条都有实测依据。

**签名里到底放了什么**（`渲染缓存.算签名()`，实测算一次 **0.7~1.7ms**）：

| 组成 | 取值 | 为什么 |
|---|---|---|
| `版本` | 常量 `签名版本 = 1` | 排版内核改了像素就 +1，避免新代码命中老图 |
| `日期` | `2026-09-14` | 时间窗、TODAY 柱带都按天走 |
| `显示配置` | 标题 / 左右时间窗 / 提醒天数 / 面板组合 | 面板用 `"全部"`（内核的 `None`）与 `[]`（三个都关）区分，两者画面不同 |
| `数据` | CSV 与 `新增预告.json` 的**内容 sha256 前 16 位** | 实测：同内容换 mtime **不**失效，内容变必然失效 |
| `图标` | `图片缓存/` 的 (文件名, 大小) | 缺头像→补下载后画面会变 |
| `背景` | **选中的那张**图的 (路径, 大小, **内容 sha256 前 16**) | 整套配色由它推导；用内容哈希 → 只改 mtime（`git checkout`/复制）不会白失效 |
| `字体` | 插件 `字体/` 的 (文件名, 大小) + `settings.额外字体` 每个文件的 (路径, 大小, mtime_ns) + `font_family` / `font_path` | 换字体画面会变 |
| `内核` | `future_buffer_hours` | **渲染期**过滤器：实测 2h 留 4 条 / 24h 留 1 条 / 72h 留 0 条 → 必须进签名 |

两条刻意的「不进签名」：

1. **背景三件套（随机 / 指定文件 / 目录）不进**——它们只是"选出哪张图"的规则，
   决定画面的是选出来的那张图。于是"指定 a.webp"与"当天恰好抽到 a.webp"同签名（画面确实一样），
   往背景目录里**新增**一张图也不会让旧缓存失效。
2. **`api_limit` 不进**——它只影响**下次抓取**多少条，抓完就体现为 CSV 内容哈希；
   **图标/随包字体只看 (名字, 大小) 不看 mtime**：重新下载或 `git checkout` 只动 mtime，
   不该让缓存白失效（"同大小换内容"这种概率极低的坏法接受为已知风险）。

#### 7.2.1 审查与讨论之后的修订（同日）

| 原方案 | 修订后 | 依据 |
|---|---|---|
| 随机背景每次请求 `random.choice` | **按自然日确定性抽签**：`候选[crc32(日期) % 张数]` | 原方案下只读预判与锁内真判定各抽一次 → 8 张背景 40 次请求分叉 4/40（最坏 ≈ (k−1)/k），会出现"说不用等却静默渲染 1.3s"；改后同一天只有一张图、不会分叉、也不会"连发两次同一张"。**阶段五进一步删掉了 `render.random_background` 开关本身**（"指定文件"已覆盖它的用途，见 §17） |
| 缓存写失败会连带丢掉已画好的图 | `存入()` 的失败**只记日志**，照常交付 | 审查实测：产物是合法 JPEG（503 字节、魔数通过），却因 `manifest` 写不进去（磁盘满/只读）把 `OSError` 抛到入口层变成"渲染失败"，下次还会重画再失败 |
| 发送路径 = 被覆盖的 `Gantt.jpg` | 发送**按签名命名、写完不再改**的缓存图；`Gantt.jpg` 只是用**原子替换**写的副本 | 宿主是"发送那一刻"才把本地文件读成 base64 的，指向会被后续请求覆盖的文件 → 并发时可能发出"别人的图"或半张图 |
| 魔数（8 字节）是唯一校验 | **入缓存**时加一道整图解码校验，发图前仍只用魔数 | 实测量级：魔数 0.03ms / `verify()` 0.05ms（拦不住截断）/ 整图解码 8.91ms。每张图只入缓存一次 → 付 9ms 值得；每次请求都解码 300KB 没必要 |
| 过期清理只在 `存入()` 里跑 | 每次出图（含命中缓存）先跑 `清理()`：过期 + 损坏 + **孤儿散图** + 残留 tmp | "一直命中缓存"或"某天没请求"时旧图会长期留着，与"过期即删"的说法不符（审查指出） |
| `_删条目` 先 pop 后 unlink | 图删不掉就**把条目放回去**，下次再试 | Windows 上文件被占用时 `unlink` 会失败；先 pop 就等于把图变成谁也认领不到的永久孤儿 |
| manifest 里只有 `版本` 字段、没人读 | 读它：不匹配就整份当空缓存；非对象（`[]`/`null`/字符串）也当空 | "改了版本号就能失效旧缓存"这条直觉要真的成立；`[]`/`null` 曾抛 `AttributeError`（审查实测） |
| manifest 里的图片路径直接用 | **必须落在缓存目录内**，否则跳过该条目 | 路径来自磁盘上的 JSON：被改坏/手工编辑的 manifest 能删掉外部文件，也能把任意可读文件当"图"发进群（调研指出的唯一"bug 即安全漏洞"） |
| 字体方案进程级缓存、永不失效 | `注册字体()` 按**字体来源指纹**（字体目录 + 额外字体 + family/path）失效 | 长驻进程里"先出图、后往 `data/font.ttf` 放字体"原本**永远不生效**（审查实测；而这是插件唯一暴露的自定义字体入口） |
| `失效时刻` 解析失败 → 当过期 | 同时容忍 `TypeError` | 传 aware datetime 时原本会抛 `TypeError` 冒出去（缓存永久未命中而不是"当过期"） |

**执行顺序（不能反）**：`刷新数据 → 清理缓存目录 → 选定背景 → 算签名 → 查缓存 → 画 → 校验 → 入缓存 → 交付`。
刷新与选背景都会改变签名，所以必须排在算签名之前。判断**只有一份**：全在锁内的 `_同步出图()` 里，
入口层不复制任何判断（它只读配置、说一句"正在准备"、出图、发图）；内核全局 `settings` 也只由
锁内的工作线程改写。

> 阶段四曾有一份"只读预判"（`查现成图()` / `更新计划()`）与一份"素材预检"（`素材问题()`），
> 阶段五全部删除：前者是为了少发一句话而复制判定路径，后者是为了提前给出更友好的文案而与
> `_同步出图()` 里的检查重复。现在素材问题通过 `素材缺失` 异常一次说明白（§17）。

**与参考物的取舍**：

- 参考物 `expires_at = min(渲染时间 + max_age, 次日 00:00)`，我们**只取后半段**（次日 00:00）。
  讨论结论是不补分段 TTL：数据内容哈希已经在签名里，日程图一天之内内容不变，
  分段 TTL 只会变成"每 N 小时重画一张只差页眉分钟数的图"（1.2s/张）；要强行重画走阶段五的 `/甘特图刷新`。
- 因此**配置面去掉了 `render.reuse_seconds`**（阶段三的临时物，schema 11 字段）；
  AstrBot 的 `check_config_integrity` 会自动剔除老用户配置里的这个键（本机模拟实例日志：
  `Config key removed: render.reuse_seconds`）。

**随机背景 × 缓存**：背景按天抽签（见上表），所以"同一份数据 + 同一天"在签名上就是**一张图**；
换天才换背景、才重画。用户想立刻换背景就改 `render.background_file`（显式指定），
"每次都要新图"的语义留给将来的 `/甘特图换背景`。

**交付路径**：图先画进 `<数据目录>/渲染缓存/渲染_<签名前16>.jpg`，校验（魔数 + 整图解码）后登记进
`manifest.json`（同目录临时文件 + `os.replace()` 原子写），再**原子地**同步一份到
`settings.output_path`（`Gantt.jpg`，给人看/给 README）。发出去的一直是那张按签名命名的文件；
命中缓存时也同步 `Gantt.jpg` 与 `警告.txt`。缓存保留最新 8 张；过期/损坏/孤儿的图会连文件一起删。

**已知上限**（都写在这里，不再散落）：

- 发图前的校验仍是魔数（8 字节文件头）："8 字节 JPEG 头 + 正文被截断"能过这道关，
  但**入缓存时**已经用整图解码挡过一轮；两者叠加后，能进缓存又被当成成品发出去的坏图需要
  "存进去之后、发出去之前被改坏"这种外部破坏。
- matplotlib 的字体表只增不减：**删掉**字体文件在本进程内仍可能解析到旧路径，
  同名同字重的**不同文件**相争时也可能落到旧的 → 这两条要重启 AstrBot 才彻底收敛。

## 9. 版本敏感点与踩坑清单

| 坑 | 事实 | 我们的对策 |
|---|---|---|
| `requirements.txt` 锁版本 | 参考物锁 `aiohttp` 与宿主冲突，最后全部解锁 | **只写裸依赖名** |
| 数据目录 API | `get_astrbot_plugin_data_path()` 是内部名字；官方文档给的是 `get_astrbot_data_path()` + 手工拼 `plugin_data/<name>` | 走文档化写法 |
| 主动推送的会话 ID | `event.message_obj.session_id` 是**裸会话号**，`Context.send_message()` 无法解析，会让推送静默失败（参考物为此真实翻过车，见其 `CHANGELOG.md:219`） | **只用 `event.unified_msg_origin`** |
| `send_message` 返回值 | 返回 `False` 表示**未投递**（不抛异常） | 必须显式判 `is False`，否则成功计数虚假 |
| `_conf_schema.json` 默认值 | 首次加载写入配置文件后，**存储值永远优先于 schema** → 以后改默认值老用户不会跟随 | 默认值变更必须写进 CHANGELOG，提示用户手动改 |
| `template_schema` 子项键名 | 必须用 `name`；`title` 不被 AstrBot 读取 | 不用 `template_schema`（我们配置简单） |
| `minimum`/`maximum` | AstrBot 原生配置渲染器**不读**它们，只是文档 | 后端必须在读取与保存两处都夹取（§8 测试 2） |
| 指令名不带斜杠 | `WakingStage` 先剥掉 wake_prefix（默认 `/`，`core/pipeline/stage.py:128`）再进指令过滤，`CommandFilter` 比较的是**无斜杠**原文 | `@filter.command("甘特图")`；斜杠只出现在给用户看的帮助/README 里（§6.3） |
| `Star.__init__` 的 config 参数 | 只有存在 `_conf_schema.json` 时加载器才传 `config`；4.28 里它是可选参数 | 入口把 `config` 声明为可缺省并回落默认值，别让加载期 `TypeError` 毙掉插件 |
| 本地图片结果的形态 | `event.image_result(本地路径)` 内部会转成 `file:///` URL（`MessageEventResult.file_image`） | 日志/测试里拿到的是 URL 不是路径；要判文件是否存在，请用 `渲染结果.图片路径` 或 `url2pathname` |
| `FT2Font.load_char()` 遇缺字形 | 字体里没有该字形时（如只剩 DejaVu 量中文）**直接段错误 0xC0000005**，catch 不住，宿主进程一起挂（matplotlib 3.11 实测） | 文本度量用 `TextToPath.get_text_width_height_descent()`（渲染器同一条 `set_text` 路径，缺字形只 warning）；详见 §10 阶段三·补 |
| `fontManager.addfont()` 不去重 | matplotlib 3.11 不按路径去重：同一支字体每 `addfont` 一次就往 `ttflist` 加一条并清 findfont 缓存（实测 ~96ms/次，长驻进程里表会一直涨） | 注册只做一次（`src/字体.py::注册字体()` 是唯一入口 + 结果缓存），别在渲染路径里反复调 |
| **长驻进程里的"一次性守卫"** | AstrBot 是长驻进程，"禁用插件→启用插件"**不会重载**已 import 的模块。`注册字体()` 原本用 `_方案 is None` 早退 → 用户出图后再往 `data/font.ttf` / `字体/` 放字体**永远不生效**（审查实测：同进程 `False`、独立进程 `True`） | 一切"只做一次"的缓存都要有**失效判据**：字体按 `字体指纹()`（目录 + 额外字体 + family/path 的 stat）失效（§5.4）。同类守卫（`绘图_排版._确保字体就绪`）用同一指纹 |
| **缓存/落盘失败别毁掉已经算好的结果** | 产物已经是合法 JPEG，但 `manifest` 写不进去（磁盘满/只读/被占）时 `OSError` 会一路穿到入口层，被翻译成"渲染失败"，用户拿不到那张好图，下次还会重画再失败（审查实测） | 入缓存是"尽力而为"：`except OSError` 只记日志，照常交付；抓取失败、复制失败同理（§7.2.1） |
| **来自磁盘 JSON 的路径要当作不可信输入** | `manifest.json` 里的图片路径被 `Path(...).unlink()` / 当"图"发出去；被改坏或手工编辑的 manifest 能删缓存目录外的文件、也能把任意可读文件发进群 | 读 manifest 时校验 `图片` 必须落在缓存目录内（`Path(...).resolve().is_relative_to(缓存目录)`），否则跳过该条目 |
| **"已解析过"不等于"内容没变"** | 公告页会被**追加**：新的剿灭轮换就写在当期活动的公告页里（`红丝绒2026/活动公告` 里的"剿灭作战关卡【默祷圣祠】追加"）。旧代码"来源已在库里就整组跳过"，于是追加内容永远看不到——实测实例那份数据缺剿灭，只有 `--bootstrap` 全量重建能捡回来（§17.5） | 增量判断要看**页面修订时间**（`获取_prts.取页面修订时间()` 一次请求拿多页），变了才重抓；候选范围按"活动是否还在 90 天内"收窄。⚠️ 多标题 `titles=A\|B\|C` 查询**不能**带 `rvlimit`（MediaWiki 报 `invalidparammix`） |
| **增量抓取算不出"不再列出"** | "这次没抓到"≠"源里没了"：公告页没变化就不重读，于是只有公告才有的条目（剿灭）每天被误报成"不再列出" | 日差只保留能可靠推出的三项：`新增 / 时间调整 / 过期清理`；被撤下的活动让它自然过期 |
| 自定义字体槽放错字体 | 用户往 `data/font.ttf` 里放一支纯拉丁字体不会报错，只会让整张图的中文变豆腐块 | 用 `get_char_index('中')` 先粗筛（**不要用 `load_char`**，见上一行），查不到就忽略并告警 |
| AI 工具 API | `astrbot.core.agent.tool` 是内部路径，且 AstrBot 自身有 reload 后插件工具失效的 issue | **第一版不做 AI 工具**；真要做时按[官方文档](https://docs.astrbot.app/dev/star/guides/ai.html)的 `FunctionTool` 子类写法 |
| 内嵌 JS | 参考物把 1845 行 JS 塞进 Python f-string，双花括号破坏一切前端工具链 | 需要前端时走 `pages/` 静态资源，**绝不内嵌** |
| 平台主动推送能力 | `platform.meta().support_proactive_message` 新版才有 | 定时推送前做能力预检（阶段五） |

**2. `文本宽()` 换真实度量（已实现，2026-09-14 起为默认）**

`src/绘图_排版.py`：`字体度量方式`（`GK_文本度量=估算|真实`，**默认 `真实`**；设 `估算` 可退回旧行为）。
"真实"**交给 matplotlib 自己量**：`TextToPath.get_text_width_height_descent(s, FontProperties(family, weight, size), False)`
（与渲染器同一条 `set_text` 路径、含字体 fallback 列表），按 `(串, 字号, family, weight)` 做 `lru_cache`；
调用点把实际绘制用的 family/weight 传进来，`截到宽()` 同步加这两个参数。

> ⚠️ **踩坑（真踩到了）**：不要用 `FT2Font.load_char()` 逐字取 `horiAdvance` 来实现它——
> 字体里**缺该字形**时（例如没有 `字体/`、只剩 DejaVu 量中文）本机实测**直接段错误 0xC0000005
> 打死进程**（matplotlib 3.11 / miniconda Python 3.13），不是能 catch 的异常，AstrBot 会跟着挂。
> `get_char_index()` 只查索引安全；`get_text_width_height_descent()` 缺字形只 warning，也安全。
> 定位过程：`tmp/崩溃_单例.py`（四个调用各跑一个进程，看退出码）。

*代价*（本机，一次 19 天窗口渲染 ~1.3s）：

| 项 | 估算 | 真实 |
|---|---|---|
| 单轮 `文本宽()` 总耗时 | 0.0001s | **冷缓存 0.019s / 热缓存 0.0000s** |
| 调用次数 | 29 | 29（`lru_cache` 29 条，命中 29 次） |
| 整图耗时 | 1.288 / 1.293s | 1.351s 冷 / 1.261s 热（在噪声内） |

*效果*（真实 vs 估算的真实偏差分布）：

| 调用点 | 次数字号 | 偏差 |
|---|---|---|
| 甘特条活动名（无衬线粗体 15） | 9 | **0.0~0.9%**（CJK 为主，估算几乎准） |
| 日期刻度 `MM/DD`（等宽 11） | 20 | **+14.9%**（估算 59.9px vs 真实 68.8px —— 唯一显著偏差） |

| 场景 | 逐像素结果 |
|---|---|
| 默认窗口（19 天） | **0 像素差**（决策一个没翻） |
| 容忍带：把估算整体乘 0.90 / 1.05 / 1.10 / 1.15 / 1.20 | **全部 0 像素差** → 默认窗口下版面决定对 ±20% 宽度误差不敏感 |
| 长窗口（`right_offset_days=60`，配置允许的上限；58 天挤在同一张图上，条宽被压到约 1/3） | **1.009% 像素差**（bbox `(192,352)-(1120,392)`）。逐条比对 94 次文字绘制，**只有 1 处不同**：活动名 `【标准池】#193 · 乌尔比安 / 仇白` 在估算下被判"条内放不下"→ 引到条外（annotate + 箭头、13 号），在真实度量下判"放得下"→ 居中写在条上（15 号）。该串估算 515.6px vs 真实 489.2px（**−5.1%**），而条宽恰好卡在两个阈值（541.6 / 515.2px）之间 |
| 日期标签清单（默认 19 个 / 长窗 29 个） | 两种模式**完全一致**（逐条比对文字与像素坐标全同）→ 差异与"画哪些日期"无关 |
| 无 `字体/` 目录（只剩 DejaVu） | 不崩、也不报错，但**出的是豆腐块图**（中文全是 `囗`）——兜底链只找 Linux 系字体，Windows 上一个都没有。要修见 §5.4 末段 |

结论：真实度量在默认窗口下**逐像素零变化**——条宽充足，各判定离边界都很远（容忍带实测 ±20%）。
它兑现价值的地方是**窗口拉长后条被压窄**：那时"名字放不放得进条内"就取决于几个百分点的宽度差，
估算会把本该留在条内的名字误判成引到条外（实测 1 处）。换字体同理（估算偏差方向会翻转）。
2026-09-14 起**默认已切到 `真实`**（代价见上表：冷 +19ms / 热 ~0，可忽略）。

| 跨日失效 | 条目的 `失效时刻 = 次日 00:00`；用"明天"去查 → 未命中；时间戳坏掉或传入 aware datetime → 也当过期（不抛异常） |
| 成品校验 | 2 字节截断/空文件/文本 → 不是成品，查缓存按未命中、`存入()` 拒绝登记；`存入()` 另做**整图解码**校验（截断正文也拦得住）；发图前仍只读魔数（已知上限见 §7.2） |
| 原子写与清理 | 并发两次后缓存目录**无 `.tmp` 残留**；`保留数=2` 时只留最新两张并删掉多余图片文件；`清理()` 删过期/损坏/孤儿散图/残留 tmp，且**图被占用删不掉时保留条目**（否则变永久孤儿） |
| manifest 韧性 | 坏 JSON、合法但非对象（`[]`/`null`/字符串）、条目不是对象、字段对不上、`版本` 不匹配 → 一律当空缓存继续跑（`未通过：无`）；**图片路径不在缓存目录内的条目被跳过**（防删外部文件 / 外发任意文件） |
| 单飞 | 清空缓存后并发两次 → **只渲染一次**（第二次在锁内命中第一次刚存的图） |
| 缓存写失败 | 把 `存入()` 打桩成抛 `OSError` → 图**照常交付**（渲染次数 1、产物魔数完整），不被翻译成"渲染失败" |
| 数据新鲜度 | 数据与预告**各按自己的 mtime** 判断该不该抓（阶段三"CSV 是今天的 → 预告一整天不再重试"的漏洞已修） |
| 缓存本身不改变画面 | 当时冷/热缓存渲染的 JPEG **字节完全一致**（`tmp/基准_渲染.py`；该脚本现在验的是"多次渲染字节一致"） |
| 字体换得动 | 审查者探针复跑：同进程内出图后再放 `data/font.ttf`，`来源=系统 → 自定义`（原本 `False`） |

## 11. 明确不做的事

1. **不注入/改写 AstrBot Dashboard 的 `index.html`**（palette 那条路）。无官方 API、版本耦合、卸载不干净。
2. **不写宿主的 `localStorage` 主题键**。用自有命名空间。
3. **不把 JS 塞进 Python f-string**。需要前端就走 `pages/` 静态资源。
4. **不锁依赖版本**（本地也会炸，与是否上架无关）。
5. **不把 `字体/`、`数据/` 提交进仓库**（体积 + 用户数据分离；`背景图/` 只有 3MB，进仓库方便换机器）。
6. **第一版不做 AI 工具**（内部 API 不稳，且 reload 有已知 issue）。
7. **不改 `src/` 下的中文模块名**（改动面大、收益低）。
8. **不为了插件砍掉 CLI**——单人调试时 CLI 比重启 AstrBot 快得多。
9. **不做 `pages/` 设置页**、**不做字体子集化**（前者 `_conf_schema` 够用，后者已经不随包字体）。
10. ~~不投入"统一系统字体"方案~~ → **已改**：2026-09-14 落地了"三层候选"（随包可放 → AstrBot
    `data/font*.ttf` → 平台字体）。但**仍然不做**逐字回退混排与跨平台字体子集化（§5.4、§14.3）。
11. **不为上架做元数据以外的适配**：不加 i18n、不自建 logo、不声明未验证的平台（阶段七只补
    `support_platforms` / `tags` 与 README）。
12. **不做渲染缓存/预热/重试/限流**：机器长期开机、单次渲染 1.4s、请求低频——这些都是为
    "高频并发"买的保险（§17.4）。真要加，先拿行为数据说话。

- ⚠️ **查中文路径别用 `Select-String` 过滤 `git ls-files`**：git 默认把非 ASCII 路径转义成 `\347\272\271...` 形式（`core.quotepath`），既匹配不到中文也匹配不到扩展名，会得到**假阴性**。用 `git -c core.quotepath=false ls-files` 或 `git ls-files -- <路径>`。
- ⚠️ **探针脚本别用 `tempfile.mkdtemp()` 造临时根目录**（2026-09-14 实测）：它在 Windows 上按 `mode=0o700` 建目录，
  CPython 会据此写一个"只给创建者 SID"的 DACL；而 DSH 沙箱里进程跑在**另一个受限 SID** 下，于是该目录
  连子目录都建不了（`PermissionError: [WinError 5]`，`icacls` 自己都读不了它的 ACL），
  而同样位置的普通 `mkdir` 建的目录一切正常。用 `根 = 仓库根/"tmp"/f"探针_{os.getpid()}_{时间戳}"` + `mkdir(parents=True)`。
- **阶段五后的验证入口**（都在 `tmp/`，gitignore 且依赖真实环境，未进仓库）：
  `check_plugin.py`（模拟 AstrBot 实例的全链路回归：导入契约 / 指令过滤 / 配置夹取 / 不留缓存 /
  快照与日差 / 并发串行 / 推送武装与幂等 / 缺背景文案）、
  `检查数据变化.py`（零依赖：合并差异语义、日差落盘与文本、坏记录容忍）、
  `检查推送.py`（零依赖推送状态与调度判据，需要 `apscheduler`，miniconda 里没有、要用 AstrBot 的解释器跑）、
  `基准_渲染.py`（多次渲染字节一致 + 耗时画像）。
  另有审查者写的 6 支故障注入探针 `审查_*.py`（字体收敛 / 接线与故障注入 / 边界 / 指纹 / 交付 / 真渲染），
  其中针对缓存的那几支**已随缓存一起作废**。
- ⚠️ **CLI 与插件的图不会逐像素一致**：CLI 不读签名缓存（调试时就是要看真实渲染），
  且两边的背景都按各自规则抽取 → 同一天 `python cli.py` 出的图与群里那张**背景很可能不同**
  （整套配色随之不同）。要对照就把 `GK_BG_DIR` 或 `render.background_file` 指到同一张图。

### 14.2 字体子集化：实测数据与坑（已不需要，留档）

> 2026-09-14 起**不随包字体**，因此这一节整体不再需要；若将来非要把字体打进包里再看。

**前提**：`src/字体.py` 的注释解释了为什么必须用静态字重——本机 `Noto Serif SC` / `Noto Sans SC` 是**可变字体（VF）**，matplotlib 没有变体轴接口，只会渲染默认实例（实测 ExtraLight(200) / Thin(100)），标题加不粗且偏细；缺 Bold 时 matplotlib 只 warning 降级、**不会伪粗**。

**实测（fontTools 4.63.0，本机 5 个字体：思源宋 Bold + 思源黑 Regular/Bold + 等宽 Regular/Bold）**：

| 覆盖方案 | 字符数 | 五字体合计 | 占 16MB 预算 |
|---|---|---|---|
| 仓库现有用字 | 1,498 | **1.45 MB** | 9% |
| 一级汉字 3755 + 仓库用字 | 4,044 | **4.22 MB** | 26% |
| 一级+二级汉字（约 6800） | 9,578 | 11.78 MB | 74% |
| CJK 基本区全集 URO | 21,435 | **30.50 MB** | ❌ 191% |
| URO + 扩展 A | 28,027 | **36.05 MB** | ❌ 225% |

拆解（仓库用字档）：衬线 Bold 602KB、无衬线 Regular/Bold 各 423KB、等宽各 19KB。等宽几乎不占体积——`Noto Sans Mono` 不含 CJK 字形（印证 `src/字体.py:33-40` "数字要单独一层"的设计）。

Noto Sans CJK 总映射 **44,810** 码位，其中 CJK 基本区 20,976 + 扩展 A 6,582。

**三个坑**：

1. **绝不加 `--retain-gids`**：该参数保留原 glyph id，会导致子集字体膨胀（[技术分析](https://blog.gitcode.com/f8ef5c9203839013f9ea0fea6a0a86ad.html)），且保留 gid 会影响 matplotlib 的文字度量——会直接破坏 `src/绘图_排版.py` 里所有 `文本宽()` / `截到宽()` / `试排()` 的像素级计算。
2. ~~**`src/绘图_排版.py:57` 的衬线判断必须重写**：子集后文件名会变，`衬线 = 衬线族 if (字体目录 / "NotoSerifCJKsc-Bold.otf").exists() else "Noto Serif SC"` 会静默落回系统可变字体。~~ **已作废**：阶段三·补之后不再有衬线族与这段判断（也为子集化少了一个坑）。
3. **字体必须放进插件目录内**（如 `assets/字体/`）才随包分发；仓库根的 `字体/` 在 `.gitignore` 里。

**现成的第三方子集产物**：[iizyd/SourceHanSansCN-TTF-Min](https://github.com/iizyd/SourceHanSansCN-TTF-Min) 已按 3500 常用字裁好思源系列，TTF/OTF 双份、全套字重。实测体积：`SourceHanSerifCN-Bold.otf` 1.28MB、`SourceHanSansSC-Regular.ttf` 1.90MB、`SourceHanSansSC-Bold.ttf` 1.88MB。**注意**：同仓库的阿里巴巴普惠体（858KB）**再分发需授权，不能用**。

**OFL 许可证**：[OFL 官网](https://openfontlicense.org/) 确认 OFL 字体**可以**打包进应用（"bundle them in apps or software subject to certain conditions"），但**修改后若原字体声明了 Reserved Font Name 则必须改名**。所以：用未修改的上游文件只需附许可证；自己重新裁剪则**必须改家族名**。

### 14.3 系统字体方案：曾经的顾虑（实测；结论已被 §5.4 推翻）

> **状态：已推翻。** 本节当年的结论是"系统字体不可行，必须随包字体"，两条理由分别是
> ①"换字体会让宽度估算系统性偏差"、②"没有衬线/无等宽"。2026-09-14 之后：① 换成了**真实度量**，
> ② 去掉了衬线、并确认平台字体的拉丁数字是**等宽数字**。于是系统字体成了默认方案（三层候选）。
> 本节保留原始实测数据，作为"字体宽度差异从哪来"的背景。

**排版会乱，乱在数字上。** 各字体字形宽度实测（`upem` 已归一，汉字宽 / 数字均宽）：

| 字体 | 汉字宽 | 数字均宽 | 相对 NotoSansCJK 偏差 |
|---|---|---|---|
| NotoSansCJKsc-Regular（现状正文） | 1.000 | 0.555 | — |
| NotoSerifCJKsc-Bold（现状标题） | 1.000 | 0.581 | +4.6% |
| Win 微软雅黑 | 1.000 | 0.586 | +5.7% |
| Win 微软雅黑 Bold | 1.000 | 0.617 | **+11.1%** |
| Win 等线 Deng | 1.000 | 0.527 | −5.1% |
| Win 黑体 / 宋体 / 楷体 | 1.000 | 0.500 | **−9.9%** |

**汉字在所有字体里都是 1.000em**（CJK 排印规范），所以中文不会乱；**数字差 10~20%**。而 `src/绘图_排版.py` 的 `文本宽()` 用的是硬编码近似值「汉字 1.0em、西文 0.55em」——**这个 0.55 正是照 NotoSansCJK（实测 0.555）配的**，换字体会让估算与实测系统性偏差，影响顶部日期轴带、底栏干员名/模组名截断、以及 `试排()` 的格宽搜索。

> **2026-09 更新（已落地）**：`文本宽()` 的**真实度量已是默认**（`GK_文本度量=估算` 可退回，见 §10 阶段三·补）。
> 实测：默认 19 天窗口下真实度量与估算**逐像素零差异**（版面决定对 ±20% 宽度误差都不敏感），
> 只有把窗口拉到 60 天、条宽被压到约 1/3 时才出现
> 1.009% 的差异，且来源是**一处活动名的"条内/条外"判定**（估算 515.6px vs 真实 489.2px，条宽正好
> 卡在阈值上）。也就是说：换字体的风险不再是"排版会漂"，而是"个别卡在边界上的名字会被判错位置"。

**更致命的是 Linux/Docker 可能没有中文字体**：Debian/python-slim 基础镜像默认不装任何 CJK 字体（[常见踩坑](https://cloud.baidu.com/article/2796068)），而 `src/绘图_图表.py:44-53` 的兜底链（`Noto Sans CJK SC` → `JP` → `Droid Sans Fallback` → `AR PL UMing CN`）在这类镜像里**一个都没有**，最后会出一整张豆腐块图。

**三平台维护成本**：Windows 可用字体（雅黑/等线/宋体/黑体，各自宽度不同，且雅黑有商用授权限制）、macOS（苹方 PingFang / 华文黑体，宽度未实测）、Linux（取决于发行版，多数默认无）——家族名、文件、宽度全都不同，"统一"做不到。

**结论**：随包字体反而是排版最稳的方案（我们知道自己用的是哪支字体）。若真要给用户选择权，加一个「字体路径」配置项即可——注意**指向系统中文字体时也必须先 `fm.fontManager.addfont(路径)` 注册**（`src/字体.py:56` 已在用这个 API），且**必须保留兜底链**作为缺字保险。

### 15.1 三个名字各是什么（2026-09-14 决定）

| 名字 | 值 | 由谁决定 |
|---|---|---|
| GitHub 仓库名 | `GanttKnights` | 你，随便叫什么；市场只要求 `repo` 是 HTTPS 的 GitHub 仓库地址 |
| **项目文件夹** | **`GanttKnights`**（曾为 `astrbot_plugin_ganttknights`） | 本地习惯，**与插件身份无关** |
| 插件身份（`metadata.yaml: name` / `plugin_id`） | `astrbot_plugin_ganttknights` / `Zrief/astrbot_plugin_ganttknights` | 社区惯例，**不动** |

**为什么允许不一致**（代码依据，见 §6.1）：

- **加载期**不校验"目录名 == `metadata.name`"：`_validate_importable_name()` 只被安装路径
  `_get_plugin_dir_name_from_metadata()` 调用（`star_manager.py:662`）。模块路径取的是**实际目录名**
  （`data.plugins.<目录名>.main`），插件名取 metadata。
- **安装期**（市场/仓库安装）会把目录改名成 `metadata.name`：先按仓库名建目录，再 `os.rename`
  （`star_manager.py:1659-1671`）。所以本地目录叫什么，都不影响别人安装后的落地目录名。

### 15.2 改名步骤（必须由人在 DSH 关闭后执行）

⚠️ **为什么不能由 DSH 里的我代做**：DSH 的 node 进程把自己的 CWD 设成了这个目录
（实测 `node.exe` 的 PEB `CurrentDirectory` = `C:\acode\astrbot_plugin_ganttknights`），
而 Windows 下**进程的当前目录会把该目录钉住**——只要 DSH 在跑，`Rename-Item` 必定报
`being used by another process`（提权也一样；沙箱不是原因，`source`/`插件`/`main.py` 这类子项都能改名，
只有根目录被钉）。没有任何 API 能从外部改别的进程的 CWD。

步骤：

1. （建议先）在你自己的终端 `git push origin main` 把本地提交推上去。
2. 关掉 DSH（结束那三个 node 进程）；顺手关掉开着该目录的资源管理器窗口（Explorer 句柄也会挡）。
3. 在普通 PowerShell 里执行下面这段（**别直接运行文件**——脚本会重命名它自己所在的目录）：

```powershell
$旧 = "C:\acode\astrbot_plugin_ganttknights"
$新 = "C:\acode\GanttKnights"
$实例联接 = "C:\Users\22378\data\plugins\astrbot_plugin_ganttknights"
$保留旧路径联接 = $true      # 想恢复"按老路径归类"的 DSH 会话就保持 $true；不要就改 $false

# 0) 关掉开着这些目录的资源管理器窗口
$sh = New-Object -ComObject Shell.Application
$sh.Windows() | Where-Object { try { $_.LocationURL -like "*astrbot_plugin_ganttknights*" } catch { $false } } |
    ForEach-Object { $_.Quit() }
Start-Sleep -Milliseconds 500

# 1) 若 $新 已存在：只接受"占位联接"（先建过新路径联接的情况），先删掉
if (Test-Path $新) {
    if ((Get-Item $新 -Force).LinkType -eq "Junction") { cmd /c rmdir $新 | Out-Null }
    else { "$新 是真实目录，请人工确认后重试"; exit 1 }
}

# 2) 重命名项目文件夹（$旧 此时应是真实目录）
Rename-Item $旧 $新 -ErrorAction Stop
"② 已重命名 → $新"

# 3) 实例插件目录联接重指（联储存绝对路径，不重指则 AstrBot 下次重启找不到插件）
if (Test-Path $实例联接) { cmd /c rmdir $实例联接 | Out-Null }
New-Item -ItemType Junction -Path $实例联接 -Target $新 | Out-Null
"③ 实例插件联接 → $新"

# 4) 旧路径兼容联接（保住老工作区归类的 DSH 会话可恢复；不需要就跳过）
if ($保留旧路径联接 -and -not (Test-Path $旧)) {
    New-Item -ItemType Junction -Path $旧 -Target $新 | Out-Null
    "④ 兼容联接：$旧 → $新（不需要时：cmd /c rmdir `"$旧`"）"
}

# 5) 验证
Get-Item $新, $旧, $实例联接 -Force |
    Select-Object FullName, LinkType, @{n = 'Target'; e = { $_.Target } } | Format-Table -AutoSize
git -C $新 status -sb
git -C $新 log --oneline -1
```

| 推送内容 | 图片 + **文字只在有话可说时才有**：日差（`🆕 新增 X；✏️ 时间调整 Y；🧹 过期清理 N 条`，来自合并侧）与**真有事**的提醒（`渲染结果.有警告`）。都没有就只发图——每天固定来一句"无需提醒"是噪音（§17.4） |
| 定时 | 自建 `AsyncIOScheduler()`（**跟随进程本地时区**，与内核 naive `datetime.now()` 一致），`CronTrigger(hour, minute)`，稳定 job id `ganttknights_daily_push` |
| job 参数 | `replace_existing=True`、`coalesce=True`、`max_instances=1`、**显式 `misfire_grace_time=600`**（库默认只有 1 秒） |
| 武装时机 | `initialize()` + **每次指令之后**都调一次 `确保任务()`（幂等：指纹 = 开关 / 该武装 / 时刻 / 会话数，变了才重建）→ WebUI 改完开关或时刻不必重启 |
| 推送动作 | 渲染**一次**（`渲染服务.出图`，锁内）→ **锁外**循环投递（文字 + 图片）→ 记账 |
| 幂等 | `已推 = {umo: 日期}`，**只记成功**；失败的会在下一次触发时重试（成功的绝不重发）→ 热重载双实例也只会各推一次 |
| 投递 | `context.send_message(umo, MessageChain([Plain, Image]))`；返回 `False`（"没找到平台实例"）与异常都算失败，记进 `上次` |
| 卸载 | `terminate()` → `调度器.shutdown(wait=False)` + `await asyncio.sleep(0)`；`_任务` 容忍 `CancelledError`；**不给插件类加 `__del__`** |
| 指令 | `/甘特图状态`（数据新鲜度 / 最近变化日期 / 推送状态 / 本会话 umo）、`/甘特图刷新`（管理员，强刷）、`/甘特图初始化`（管理员，**全量回溯**） |
| 配置 | `push.enabled`(false) + `push.time`("08:00")，共 2 个字段；后端把坏时刻归一/退回默认（`规范化时刻()`） |

**判据复核**（`tmp/检查推送.py` 零依赖快测 + `tmp/check_plugin.py` 模拟实例，均 `未通过：无`）：

| 判据 | 实测 |
|---|---|
| 无配置不建调度器 | 开关关 → 不建；开关开但**没有任何会话** → 也不建（`推送：已开启（08:00），但还没有可用会话`） |
| job 形状 | `coalesce=True` / `max_instances=1` / `misfire_grace_time=600` / 稳定 id；重复调用不会建出第二个 |
| 只渲染一次 | 假发送 + 假渲染：一次 `推一次()` 里渲染调用 **1** 次、三个会话各收到一条（文字 + 存在的图） |
| 幂等 | 第二次 `推一次()` → `已经推过，跳过`；把某个会话打成失败 → 只重试它（`成功 0 / 失败 1` 记进状态） |
| 状态逻辑 | 会话去重且最近在后、上限 20；坏 JSON / 非对象 / 字段类型不对 → 当空状态；无 `.tmp` 残留 |
| 状态页 | 含数据新鲜度、**最近快照日期**、推送武装情况、**本会话 umo**（用户自助配置推送的前提） |
| 推送文案 | 没有日差也没有真警告 → **不带文字**（免得每天一句废话）；两者都有 → 日差在前、提醒在后 |

### 16.2 为什么不做（第一性原理下的取舍）

| 没做 | 为什么 |
|---|---|
| **预热任务**（提前 N 分钟渲染） | 渲染 1.2~1.5s。"提前渲染好"只是把同一件事挪个时间，却要多一个 job、一段配置和一份状态 |
| **退避重试** | 数据文件 mtime 天然就是重试判据（当天任何触发都会重抓）；投递失败记进状态、`/甘特图状态` 可见 |
| **平台能力预检** | `meta().support_proactive_message` 是 4.28 新增且**默认 True**（信不过）；发一次并把结果记下来比读字段可靠 |
| **多会话限流 / 错峰 `sleep(2s)`** | 目标通常 1~2 个会话，顺序 `await` 本身就够 |
| **SQLAlchemyJobStore** | 停机错过的每日推送**就该静默跳过**（宁可不推，也不在重启后补推过期图）；`MemoryJobStore` 正好是这个语义 |
| **配置里填目标会话列表** | 让用户"抄一段 umo 再填进配置"是把内部标识推给用户；参考物甚至在 schema 里让用户发一条它自己都没实现的 `/sid` 指令 |
| **`/甘特图警告`** | 每日推送已经带上警告文本；单独一条指令只是重复一次渲染结果的搬运。真需要时 5 行就能加 |

### 16.3 用到的宿主/库硬事实（照此实现，别再踩）

- **宿主关停顺序**：先 `cron_manager.shutdown()`（`astrbot/core/core_lifecycle.py:392`）**再**调插件
  `terminate()`（`:396-398`）→ 不能用宿主的调度器；该 API 也未文档化（官方文档全站无 APScheduler 字样）。
- **APScheduler 3.11.3**：`misfire_grace_time` 库默认 **1 秒**；`AsyncIOScheduler.start()` 必须在事件循环里
  调用（`asyncio.get_running_loop()`）→ 只能放 `initialize()` 或指令处理函数；`start()` 不幂等；
  `shutdown()` 是 `call_soon_threadsafe` 投递，之后要 `await asyncio.sleep(0)`；
  `AsyncIOExecutor` 会 cancel 未完成协程 → 任务体要容忍 `CancelledError`。
- **绝不给插件类加 `__del__`**：`astrbot/core/star/star_manager.py:2022-2041` 是 `if __del__ … elif terminate`
  → 加了 `__del__` 会让 `terminate()` 永不执行，热重载后双实例双推送。
- **投递 API**：只用 `event.unified_msg_origin`（裸 `session_id` 会在
  `message/message_session.py:26` 的 `split(":", 2)` 处抛错）；`send_message` 返回 `False` 只表示
  "没找到匹配的平台实例"（`star/context.py:626`），非法 umo 直接 `ValueError`；消息链要包成
  `MessageChain([...])`（照参考物 `main.py:1371-1372`）。
- **`requirements.txt` 要写 `APScheduler`**：AstrBot 自己依赖 `apscheduler>=3.11`，但那是它的依赖，
  换机器时插件不该赌它存在。

## 17. 第一性原理复盘：砍掉的代码与建议（2026-09-14）

目标只有三句：**按需出一张图 / 每天推一次 / 能上架**。所有"看起来专业但与这三句无关"的东西都该被质疑。
下面是这一轮真正删掉的东西（以及为什么），以及仍然保留的复杂度的理由。
判据：**它是否让用户可感地更好？它是否换来某条正确性保证？它的成本（代码面 / 内存 / 常驻路径）是否可量化？**

### 17.1 删掉的（连同它们带来的负担）

| 删掉的 | 当时为什么加 | 为什么删 |
|---|---|---|
| `渲染服务.查现成图()` + `更新计划()` + 两条进度文案 | 命中缓存时"不说'请稍候'"更精致 | 为了少发**一句话**，在事件循环里复制了一条判定路径（算签名 + 查 manifest），并让"预判 vs 真判定"成为一类 bug（审查实测 8 张背景 40 次请求分叉 4/40）。现在入口层无条件发一句中性的"正在准备…"，渲染服务只剩 `出图()` / `产物可用()` / `准备matplotlib环境()` |
| `渲染服务.素材问题()` 预检 | 空背景目录要"提前"给友好文案 | 与 `_同步出图()` 里的检查重复。改成 `素材缺失` 异常（带"是目录空还是指定文件不在"），入口层一次翻译成人话——顺带补上了一个真漏洞：**`background_file` 写错文件名原本会静默画出一张默认配色的图**（内核读不到背景会回退默认配色） |
| `render.random_background` 配置项 | "随机 / 固定 / 指定"三件套 | `指定背景文件` 已经表达了"用哪张"；留一个"固定用第一张"的开关只是让两种规则互相覆盖。现在规则唯一：**指定了就用它，否则按日抽签**（schema 11 → 10 字段，阶段五加推送后是 12） |
| 内核 `lru_cache`（背景解码 + 配色推导） | 省 ~262ms/次 | 签名缓存已经把"同一天重复出图"整个消灭 → 一个进程里只渲染 1~2 次；省下的 0.26s 换 **8.8MB/张常驻内存** 与"忘了把指纹放进缓存键就永远发旧图"这类正确性风险。实测冷/热渲染字节完全一致 → 删掉不改变任何像素（单次渲染 1.18s → 1.46s，用户无感） |
| `_同步一份()` 的"内容相同就跳过" | 省一次 300KB 写 | 要做一次 **600KB 读**才能省一次 300KB 写——**净亏 I/O**。改成永远原子替换（3 行 → 8 行，但语义单一） |
| `push.target_sid_list` 配置 + 让用户"抄 umo" | 目标会话可配置 | 谁发过 `/甘特图` 就记住谁，用户不需要知道 umo 是什么；`/甘特图状态` 回显 umo 只是给好奇的人看 |
| 预热任务 / 退避重试 / 平台能力预检 / 多会话限流 / `/甘特图警告` | 参考物里都有 | 逐条见 §16.2：都是"听起来专业"，对 1~2 个会话、1.2s 渲染的量级没有可感收益 |

### 17.2 保留下来的复杂度，以及它们换到了什么

| 保留的 | 成本 | 换到了什么 |
|---|---|---|
| 签名缓存（`插件/缓存.py`） | ~300 行 | 用户可感：重复请求 10ms 而不是 1.4s；跨重启复用 |
| manifest 原子写 + 魔数 + 入缓存时整图解码 | ~40 行 + 9ms/张 | 不发坏图；被外部改坏的目录也能自愈 |
| 签名里放内容哈希（数据 / 背景） | 1~3ms/次 | "重爬一次但内容没变"不重画；`git checkout` 不动 mtime 也不重画 |
| 字体指纹失效（`src/字体.py`） | ~30 行 + 0.1ms/次 | 长驻进程里"放个字体"能立刻生效（原本要重启 AstrBot） |
| `清理()`：过期 + 损坏 + 孤儿 + 残留 tmp | ~25 行 | 缓存目录有界；Windows 删不掉时不制造永久孤儿 |
| `manifest` 路径容纳性校验 | 3 行 | 挡住"删缓存目录外的文件 / 把任意可读文件发进群"（唯一的"bug 即安全漏洞"） |
| 推送的幂等记账 | ~20 行 | 热重载双实例不会重复推；失败可见 |
| 会话记忆（而不是配置会话 ID） | ~15 行 | 用户零配置；没有"抄一段内部标识"的步骤 |

### 17.3 结论式的几条规矩（用于将来的"要不要加"）

1. **不复制判定**：同一件事只判一次，判在离副作用最近的地方（锁内）。"提前预判"只有在
   *能避免昂贵副作用*（如省掉一次 30s 网络抓取）时才值得，且预判结果必须**透传**给真判定。
2. **优化的收益要能被用户感知**：省 0.26s 换 8.8MB 常驻、或省一次写换两次读，都不算优化。
3. **配置项要能回答"用户什么时候会改它"**：答不上来就别暴露（字体、请求条数、复用窗口、
   随机背景开关都是这样被砍的）。
4. **让用户抄内部标识是设计缺陷**：能自动记住的（会话）就自动记住。
5. **常驻进程里一切"只做一次"的缓存都要有失效判据**（字体、签名、配置读取）。
6. **先问"这个产品每天真正要回答什么"**：答案之外的机制（缓存、预热、重试、限流）
   都要能被这句话否掉。下面 §17.4 就是照这条又砍了一轮。

### 17.4 第二次复盘：连缓存一起删掉，改成"每日快照对比"（2026-09-14 晚，用户拍板）

**先修正行为模型**：机器是**长期开机**的 → 之前设想的"电脑关着所以错过推送"不成立，
`misfire_grace_time=600`、以及我提议的"开机补推"都不需要（后者**没有实现**，别再加）。

**用户给的那句话是全部设计的起点**：
> "我们几乎只需要爬取并和昨天的数据对比就行，完全不需要复杂的缓存等东西，性能在这里不重要。"

于是删掉的东西（连同它们的代价）：

| 删掉的 | 规模 | 为什么 |
|---|---|---|
| `插件/缓存.py` 整个文件 | ~380 行 | 它解决的问题（同一天第二次请求少画一次）在"低频请求 + 1.4s 渲染"下不值这个复杂度；而它带来的 8 类 bug 全都被那次对抗性审查真实抓到过（预判分叉、manifest 非对象、永久孤儿、路径容纳性、写失败毁图、发送路径竞态、跨日/时区、删不掉文件） |
| 签名（7 个组成部分 + sha256 + `签名版本`） | ~60 行 | 签名只为"给缓存找键"存在；没有缓存就没有键 |
| manifest / 原子写 / 跨日失效 / 保留数 / 孤儿与 tmp 清理 / 路径容纳性校验 | ~120 行 | 全是缓存的生命周期管理 |
| 入缓存时的整图解码校验 | ~15 行 | 见 §7.2.1 的"已知上限"整段不再需要；发图前仍保留**廉价的魔数校验**（防"根本没画出来"） |
| `渲染缓存/` 目录与 `/甘特图状态` 里的缓存统计 | — | 磁盘上不再有第二份图；状态页改成报"数据新鲜度 + 最近快照 + 推送情况" |
| 发送时把图复制到 `Gantt.jpg`（含"内容相同就跳过"的负优化） | ~20 行 | 现在**直接原子写到 `Gantt.jpg`**（临时文件 + `os.replace`），发出去的就是它——少一次 300KB 拷贝，也不用再担心"发送路径指向会被覆盖的文件"（同一天同一份数据渲染出来的字节本来就一致） |

**换来的新东西**（这才是这个产品每天的主体）：

| 新增 | 规模 | 干什么 |
|---|---|---|
| `汇总_活动.合并差异`（`src/汇总_活动.py`） | ~25 行 | **合并动作自己回答"变了什么"**：它手里本来就有原有内容与本次抓取的内容，天然知道谁是新来的、谁被改了、谁过了清理线（用户 2026-09-14 指出："爬取数据的时候需要看有哪些增量、哪些过期，这天然就是快照对比"） |
| `src/数据变化.py` | ~130 行 | 把那次差异**按天落盘**（`数据/最近数据变化.json`）：合并一天只发生一次，而推送在几小时后、还可能经历重载；同一天第二次合并不改写，保证早上推的和晚上看的是同一份日差 |
| `渲染结果.变化` / `渲染结果.有警告` | 2 个字段 | 日差文本随结果走（CLI、推送、状态页共用）；`有警告` 用来判断那句回落文案有没有信息量 |
| 推送文案规则（`推送服务._文案()`） | ~10 行 | **先日差、再真有事时的提醒；都没有就一句都不发**（每天固定一句"无需提醒"是噪音） |
| CLI 顺手打一行日差 | 3 行 | `python cli.py` 也能看到"今天变了什么" |

> ⚠️ **第一版做错了两处，都在这轮改掉了**：
> ① 最初是"每天存一份完整活动表快照、事后拿 CSV 对比"——多余（合并侧本来就知道），已删；
> ② 日差里曾有一项「不再列出」（曾有过、这次没抓到的），但抓取是**增量**的
> （公告页没变化就不再重读），"这次没抓到"推不出"源里没了"——实测它每天把只有公告才有的
> 剿灭误报成"不再列出"。**这一项已删除**，日差只剩 `新增 / 时间调整 / 过期清理` 三项。

**判据复核**（`tmp/检查数据变化.py` 零依赖 + `tmp/check_plugin.py` 模拟实例，均 `未通过：无`）：

| 判据 | 实测 |
|---|---|
| 合并差异语义 | 新增只报**留得下来**的条目（卡池一览每天带回几十条早已结束的，进来就被清理线删掉 → 不算新增）；改动 = 同名但时间/类型变了；`过期清理` 只数**原本就在 store 里、这次没留下来**的 |
| 首次建立 | `原有条数 == 0` → 标记 `首次`，不报"新增 300 条"，文本为空串 |
| 日差落盘 | 当天第一次合并写下记录；同一天再合并不改写；换一天改写且 `对比日期` 取上一次的日期；记录不是今天的 → 不附文字 |
| 日差文本 | `与 2026-09-13 相比：🆕 新增 甲、乙、丙、丁、戊 等 6 个；✏️ 时间调整 庚；🧹 过期清理 3 条`（超过 5 个折叠） |
| 容错 | 坏 JSON / 非对象 / 字段类型不对 → 当没有记录（个别坏字段只退化那一个字段），不抛异常、不影响出图 |
| 幂等 | 同一天第三次抓取（删掉记录强制重算）→ `新增 0 / 改动 0 / 过期清理 0`，不来回跳 |

| 改动 | 为什么 |
|---|---|
| 候选范围改成 `进行中 ∪ 结束时间在 90 天内`（`公告复查窗口天`） | 追加剿灭轮换的公告挂在"当期活动"名下，窗口只要覆盖"轮换仍在跑"的时长 |
| 用**页面修订时间**判断"公告页有没有被追加"（`获取_prts.取页面修订时间()`，**一次** `titles=A\|B\|C…` 请求拿全部候选页的最新修订时间；⚠️ 多标题查询不能带 `rvlimit`，MediaWiki 会报 `invalidparammix`） | 逐页重抓太贵（每天几十页），而"解析过"不能当"内容没变"——公告页会被追加 |
| 记录"上次抓到时是哪一版"（`数据/公告修订.json`），只有**变了**才重抓 | 每天只多一次廉价请求 + 0~2 次页面抓取 |
| 修订记录**不存在**时（首次/升级后第一次）对窗口内候选做一次全量复查 | 一次性自愈：把以前"因为解析过而整段跳过"时漏掉的追加内容补回来（实例那条剿灭就是这么丢的） |
| 公告页没变化的组**整组不动**（不再用 API 时间写兜底行） | 否则同一条记录会在"公告时间"与"API 时间"之间每天来回跳（实测踩到） |

**实证**（`tmp/探_剿灭修复.py`：把实例数据复制一份，跑真实的 `更新数据`）：

```text
实例副本：共 10 行；长期/剿灭 = ['重启锚点', '【肉鸽】沉沦者的黑流树海']
第一次抓取后：共 11 行；长期/剿灭 = [... , '【剿灭】默祷圣祠']
合并差异：新增 1 / 改动 0 / 过期清理 0
日差文本：本次更新：🆕 新增 【剿灭】默祷圣祠
修订记录写了 5 页
第三次抓取（删掉记录强制重算）：新增 0 / 改动 0 / 过期清理 0
丢掉的行：[]   新增的行：['【剿灭】默祷圣祠']   时间变了的行：[]
```

即：**日常抓取（不是 `--bootstrap`）就能把剿灭补回来，且不会反复抖动**。
下一次轮换换期时同样会被修订时间变化触发（无论那个活动是否已经结束）。

#### 17.5.1 但增量扫描有边界，所以插件也要有"初始化"通道

90 天窗口只能覆盖"最近的活动"。**wiki 会复用老活动页**：对比"仓库那份（`--bootstrap` 重建）"
与"实例那份（插件日常抓）"时，仓库多出的 10 行**全都是未来/复刻排期**，来源是 2025 年的老活动页：

```text
仓库 20 行（--bootstrap 重建）｜实例 10 行（插件日常抓）
只在仓库里（全量回溯才拿到的）：
  【0011/飙】系列，限        2026-11-25 → 2026-12-09  类型=1  来源=揭幕者们2025
  【剿灭】默祷圣祠            2026-07-27 → 2026-10-26  类型=99 来源=红丝绒2026
  出苍白海2025 关卡          2026-12-19 → 2026-12-29  类型=1  来源=出苍白海2025
  揭幕者们2025 / … 关卡 / 组合包 / 留影烁今 / 未许之地 / 礼包限时上架 …
```

所以 CLI 的 `--bootstrap` 不能被插件落下，补法是**两条**（`插件/渲染.py` + `插件/指令.py`）：

| 通道 | 行为 |
|---|---|
| **自动** | `_刷新数据()` 发现**还没有 CSV**（全新安装、或用户删了数据）→ 本次自动做一次全量回溯，日志写明"等价 cli.py --bootstrap"。用户不需要知道 bootstrap 是什么，装完第一次出图就是完整数据 |
| **手动** | `/甘特图初始化`（别名 `/甘特图全量更新`，管理员）→ `出图(强制刷新=True, 回溯已结束=True)`，跑完把日差一并回给用户。用于"数据看着缺内容"或 wiki 刚排了复刻 |

**判据复核**（模拟实例，`未通过：无`）：

| 判据 | 实测 |
|---|---|
| 全新安装自动回溯 | CSV 不存在 → `_刷新数据` 调用 `更新数据(回溯已结束=True)`（日志：`还没有活动数据（全新安装）→ 本次自动做一次全量回溯`） |
| 日常不回溯 | CSV 存在 → `回溯已结束=False` |
| 显式初始化 | `/甘特图初始化` → `回溯已结束=True` |
| 权限 | `刷新` 与 `初始化` 都挂 `PermissionType.ADMIN`；`出图` 不受限 |
| 指令注册 | 5 条：`甘特图`(+2 别名) / `甘特图状态` / `甘特图刷新`(+1) / `甘特图初始化`(+1) / `甘特图帮助`，互不串味 |

**代价（写清楚，别假装没有）**：

- 同一天内第 N 次请求要重新等 ~1.4s（有"正在准备"文案兜住）；群里有 3 个人同时问就是 3 次串行渲染；
- 跨重启不再复用任何图；CLI 与插件各画各的；
- 换来的好处是：**任何时刻发出的图都等于"当前数据的真实渲染"**——不存在陈旧图、失效策略、
  缓存目录损坏这一类问题（这一类问题占了阶段四审查发现的一半）。
